# ADR-001: Разделение LLM и менеджера диалога

Статус: `accepted`

## Контекст

Голосовой бот должен одновременно решать две разные задачи:

1. понимать смысл пользовательской реплики и формировать содержательный ответ;
2. надёжно управлять состоянием телефонного разговора, перебиваниями, эскалацией и SIP-командами.

LLM хорошо подходит для смысловой интерпретации и планирования ответа, но её вывод недетерминирован. Состояние звонка, допустимые переходы и критичные действия вроде перевода на оператора должны выполняться предсказуемо.

## Решение

Вводится отдельный компонент `Dialogue Manager`, реализующий конечный автомат состояния диалога и являющийся владельцем состояния разговора.

Логический путь подготовки и исполнения ответа разделяется на три границы:

- `Dialogue Manager / FSM` принимает прикладные решения, выбирает разрешённый `skill_id` и generation policy,
  проверяет переходы и владеет необратимыми действиями;
- `Skill & Prompt Manager` по финальному ходу, контексту, знаниям и разрешённому профилю формирует версионируемый
  typed `LlmRequest`; он не принимает SIP-решений и не обращается к Ollama;
- `LLM Facade` предоставляет внутренний API и владеет IPC к локальному inference-процессу; он не выбирает skill,
  не редактирует смысл пользовательского запроса и не исполняет SIP-команды.

LLM не управляет SIP напрямую. Она передаёт менеджеру диалога структурированное решение, содержащее как минимум тип действия и, если нужно, текст ответа:

```json
{
  "action": "answer",
  "text": "Ответ пользователю"
}
```

Примеры действий:

- `answer` — подготовить ответ для TTS;
- `clarify` — запросить уточнение;
- `offer_transfer` — предложить подключить оператора;
- `transfer` — запросить перевод звонка;
- `hangup` — завершить разговор.

Dialogue Manager:

- хранит и изменяет состояние разговора;
- проверяет, допустимо ли предложенное LLM действие в текущем состоянии;
- управляет историей и файловым контекстом разговора;
- обрабатывает перебивания, отмену генерации и таймауты;
- отправляет команды в SIP-адаптер;
- инициирует создание итогового отчёта после завершения разговора.

Кроме того, Dialogue Manager передаёт `Skill & Prompt Manager` разрешённый тип обработки и ограничения ответа.

Skill & Prompt Manager:

- выбирает версию шаблона, skill policy, output schema и generation profile;
- объединяет финальный пользовательский ход с компактным контекстом и retrieval-фрагментами;
- формирует `LlmRequest` и сохраняет идентификаторы/версии prompt-профиля для диагностики и benchmark;
- передаёт запрос только в `LLM Facade`, не меняя семантику пользовательского текста.

LLM Facade:

- скрывает внешний HTTP/stream-протокол локального inference-процесса;
- переводит внутренний `LlmRequest` в запрос inference и возвращает typed stream/status/structured result;
- выполняет cancellation и stale-result policy, но не владеет состоянием диалога.

Семантическая LLM отвечает за:

- понимание смысла реплики;
- использование истории и найденных знаний;
- выбор предлагаемого смыслового действия;
- формирование текста для пользователя.

SIP-адаптер остаётся отдельной границей системы и исполняет команды менеджера диалога: ответить на звонок, завершить звонок, перевести звонок и передать аудио.

## Рассмотренные альтернативы

### LLM напрямую управляет SIP и состоянием разговора

Отклонено. Произвольный текстовый вывод модели трудно надёжно преобразовать в команды, а ошибки модели могут привести к некорректному состоянию звонка или неправильному переводу.

### Один детерминированный сценарий без отдельного менеджера диалога

Отклонено. Такой подход не покрывает полноценный контекстный диалог, уточняющие вопросы, перебивания и динамическую эскалацию.

### LLM отвечает только текстом, а действие выводится из текста эвристиками

Отклонено. Определение намерения по готовому тексту ответа создаёт лишнюю неоднозначность. Действие должно быть отдельным структурированным полем результата LLM.

## Последствия

Положительные:

- SIP и критичные переходы состояния не зависят напрямую от свободного текста LLM;
- конечный автомат можно тестировать без запуска моделей;
- обработка перебиваний, отмен и таймаутов становится явной;
- контекст разговора и итоговый отчёт имеют одного владельца;
- модели ASR, LLM и TTS можно заменять независимо от SIP-слоя.
- шаблоны, навыки и generation profiles можно отдельно тестировать и сравнивать вместе с моделью; влияние краткой
  инструкции на задержку и длину ответа становится наблюдаемым, а не скрытым в коде FSM или HTTP-клиента.

Отрицательные:

- появляется дополнительный компонент и межкомпонентный контракт;
- потребуется определить схему структурированного результата LLM;
- часть решений модели может быть отклонена менеджером как недопустимая в текущем состоянии;
- потребуется явно описать состояния, события и переходы.
- появится дополнительная boundary между контекстом и inference-фасадом, а prompt/profile versioning станет частью
  contract/evidence-процесса.
