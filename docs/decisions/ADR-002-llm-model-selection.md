# ADR-002: Выбор локальной LLM для MVP

Статус: `proposed`

## Контекст

LLM должна работать локально на NVIDIA RTX 5060 Ti с доступным объёмом видеопамяти до 16 ГБ. При этом на том же GPU могут выполняться ASR и TTS, а пользовательская задержка от окончания реплики до первого полезного звука должна укладываться в общий ориентир 200–500 ms.

Первоначальный вариант этого ADR составлялся для поколения Qwen3. С тех пор появились Qwen3.5, Qwen3.6 и Qwen3.8, поэтому старый shortlist нельзя считать актуальным без повторной проверки.

Модель должна:

- хорошо работать на русском языке;
- поддерживать многоходовой диалог и краткий контекст разговора;
- использовать найденные фрагменты локальной базы знаний по естественным наукам;
- уметь возвращать ограниченный структурированный результат с действием и текстом;
- поддерживать потоковую генерацию или другой способ уменьшения времени до первого фрагмента;
- работать с короткими ответами, пригодными для телефонного TTS;
- допускать локальный inference и квантование.

Сравнение кандидатов должно проводиться на том же prompt-контракте, который используется прикладным путём: через
`Skill & Prompt Manager`, с одинаковыми output schema и generation profile. Версия шаблона и профиля является частью
экспериментального условия; изменение короткой инструкции считается отдельным вариантом benchmark, а не незаметной
настройкой модели.

Переобучение модели не планируется. Знания предметной области подключаются через retrieval/RAG.

## Предварительное решение

Финальный выбор пока не утверждён. Текущий shortlist для проверки:

- **Qwen3.5-9B** в 4-битной квантизации — основной новый кандидат;
- **Qwen3.5-4B** — быстрый кандидат для baseline и, возможно, speculative-анализа;
- **Qwen3-8B** в 4-битной квантизации — baseline скорости и совместимости;
- **Vikhr-Llama3.1-8B-Instruct-R** — русскоязычный контрольный baseline;
- **Qwen3.6-27B** и **Qwen3.8-27B** — stretch-кандидаты по качеству, требующие отдельной проверки помещаемости и задержки;
- **Qwen3.6-35B-A3B** — экспериментальный MoE-кандидат; 3B активных параметров не отменяют необходимости хранить примерно 35B параметров, поэтому для 16 ГБ VRAM он не считается реалистичным основным вариантом.

Qwen3-14B, ранее рассматривавшийся как резерв, больше не является приоритетным: при сопоставимом ограничении памяти предпочтительнее сначала проверить более новые модели семейства Qwen3.5/Qwen3.6/Qwen3.8.

Для телефонного диалога режим рассуждений по умолчанию не используется. Длинное скрытое рассуждение увеличивает задержку, а пользователю нужен короткий проверяемый ответ или явное предложение перевода на оператора.

Для speculative-обработки промежуточного ASR используется non-thinking/instruct-режим. Предварительный запрос может быть отменён и заменён новым запросом по мере стабилизации текста. Только финальный ASR-текст может породить окончательное действие FSM и ответ для TTS.

## Рассмотренные альтернативы

### Qwen3.5-9B

Текущий основной кандидат.

Плюсы:

- более новое поколение по сравнению с исходным Qwen3-8B;
- размер, реалистичный для 16 ГБ после квантизации;
- подходит для повторных коротких speculative-запросов;
- может использоваться в том же локальном inference-контуре, что и более крупные Qwen-модели;
- лицензия Apache-2.0.

Минусы и риски:

- фактическая помещаемость зависит от формата квантизации, KV-кэша и совместной работы с ASR/TTS;
- новая multimodal-архитектура может потребовать отдельной проверки text-only deployment;
- качество русского телефонного диалога и structured output нужно измерить на нашем наборе.

### Qwen3.5-4B

Быстрый baseline и кандидат для предварительного анализа неполного ASR-текста.

Плюсы:

- большой запас VRAM и потенциально минимальное время до первого токена;
- удобен для intent extraction, выделения сущностей и предварительного retrieval;
- лицензия Apache-2.0.

Минусы и риски:

- может уступить более крупным моделям в многоходовом диалоге и работе с несколькими фрагментами знаний;
- не следует заранее считать его достаточным для финальных ответов.

### Qwen3-8B

Плюсы:

- 8,2 млрд параметров — разумный размер при совместной работе с ASR и TTS на GPU 16 ГБ;
- лицензия Apache-2.0;
- заявлена поддержка более 100 языков и диалогов на нескольких ходах;
- есть переключение между thinking и non-thinking режимами;
- предусмотрены возможности интеграции с инструментами и структурированными действиями;
- есть поддержка локальных runtime и готовых квантизированных вариантов.

Минусы и риски:

- нужно корректно настроить chat template и явно отключать thinking;
- фактическая скорость зависит от выбранного runtime, квантизации, длины контекста и конкуренции с ASR/TTS;
- качество русского языка нужно проверить на наших диалогах, а не выводить только из общих benchmark.

### Vikhr-Llama3.1-8B-Instruct-R

Плюсы:

- модель позиционируется для русского и английского языков;
- лицензия Apache-2.0;
- в материалах модели присутствуют русскоязычные данные и отдельная оценка RAG;
- естественный кандидат для сравнения именно на русскоязычном телефонном диалоге.

Минусы и риски:

- модельный стек основан на Llama 3.1 и выпущен раньше Qwen3.5/Qwen3.6/Qwen3.8;
- возможна уступка Qwen3 в общем следовании сложным инструкциям и рассуждении;
- качество и скорость нужно проверять на том же формате структурированного результата.

### Qwen3.6-27B и Qwen3.8-27B

Плюсы:

- более новые поколения и потенциально более высокое качество на сложных вопросах и длинных связях между репликами;
- поддержка современных локальных inference-runtime;
- лицензия Apache-2.0.

Минусы и риски:

- 27B параметров в 4-битном представлении требуют примерно 13,5 GB только для идеализированных весов, без служебных данных, KV-кэша и runtime;
- Qwen3.8-27B является vision-language-моделью, хотя наш сценарий использует только текст;
- одновременная работа ASR, LLM и TTS на одной 16-гигабайтной карте, вероятно, потребует агрессивной квантизации или offload;
- повторные speculative-запросы могут оказаться слишком дорогими по задержке.

Модели остаются stretch-кандидатами для эксперимента с качеством, но не стартовым выбором MVP.

### Qwen3.6-35B-A3B

Плюсы:

- современная MoE-архитектура;
- около 3B активных параметров на шаг, что потенциально снижает вычислительную стоимость декодирования;
- потенциально высокое качество.

Минусы и риски:

- всего 35B параметров должны быть доступны в памяти модели, поэтому «3B active» не означает размер 3B;
- идеализированный 4-битный объём весов уже превышает доступные 16 ГБ с учётом служебных данных;
- offload, вероятно, несовместим с целевой задержкой;
- не рассматривается как основной кандидат для MVP.

### Gemma 3 12B

Плюсы:

- заявлена поддержка более 140 языков;
- большой контекст — до 128K токенов;
- доступна локальная inference-инфраструктура и квантизации.

Минусы и риски:

- используется отдельная лицензия Gemma, а не Apache-2.0;
- мультимодальные возможности не нужны для нашего текстового LLM-контура;
- размер 12B создаёт заметное давление на VRAM и задержку;
- приоритет русского языка и качество RAG для нашей задачи нужно проверять отдельно.

### Компактные модели Qwen3 1.7–4B

Плюсы:

- минимальное потребление памяти;
- потенциально лучшая скорость и больший запас для ASR/TTS;
- могут быть полезны как baseline или быстрый fallback.

Минусы и риски:

- вероятное снижение качества сложного многоходового диалога;
- больше риск ошибок при работе с несколькими фрагментами базы знаний;
- выше требования к правилам эскалации и проверке ответа.

Для основной LLM MVP такой размер пока не выбирается.

## Контракт LLM и ограничения интеграции

LLM не управляет SIP напрямую. Она возвращает менеджеру диалога структурированный объект:

```json
{
  "action": "answer",
  "text": "Краткий ответ пользователю"
}
```

Допустимые значения `action`:

- `answer` — ответить пользователю;
- `clarify` — запросить уточнение;
- `offer_transfer` — сообщить об ограничении и предложить оператора;
- `transfer` — запросить перевод по адресу из конфигурации;
- `hangup` — завершить разговор.

Менеджер диалога проверяет JSON, состояние автомата и допустимость действия. Модель не выбирает SIP-адрес оператора и не вызывает SIP-команды.

В prompt модели передаются компактное резюме разговора, последние релевантные реплики, текущая реплика пользователя, состояние диалога и найденные фрагменты базы знаний. Полная история не должна бесконечно накапливаться в prompt.

Фактическая сборка этого prompt выполняется `Skill & Prompt Manager`, а не `Dialogue FSM` и не `LLM Facade`. В evidence
фиксируются `skill_id`, версия шаблона/profile, состав входного контекста, время от получения финального хода до первого
полезного результата, полное время генерации и число выданных токенов. Это позволяет отдельно оценить выигрыш от
формулировки инструкции, не приписывая его архитектуре модели.

Текст ответа должен быть русскоязычным, коротким, без Markdown и пригодным для немедленной передачи в TTS. Содержимое thinking, если оно используется при эксперименте, не передаётся пользователю и не сохраняется в истории как ответ бота.

## Зафиксированная граница выполнения C3

В рамках C3 владелец проекта принял process-isolated вариант исполнения. Primary-кандидат Qwen3.5-9B в GGUF Q4_K_M
запускается локальным Ollama-сервисом с bundled native `llama.cpp` runner в отдельном процессе. Основной процесс на
free-threaded CPython не импортирует native inference-модуль и обращается к сервису через рабочий HTTP IPC на
`127.0.0.1`.

Это не внешний inference API: модель и inference-сервис работают локально. Dispatcher не становится HTTP-прокси для
полезной нагрузки и сохраняет ownership control plane; LLM-адаптер напрямую обменивается запросами и результатами с
inference-процессом. Решение закрывает C3 как `pass_with_isolation`, но не объявляет весь LLM-контур production-ready и
не заменяет дальнейшую проверку совместной работы с ASR/TTS.

## План проверки

Кандидаты сравниваются на одной машине, одном runtime и сопоставимой квантизации, насколько это технически возможно. Набор проверки должен включать:

- вопросы по естественным наукам, ответы на которые есть в RAG-контексте;
- вопросы, для которых в контексте недостаточно данных;
- контрольный negative case: осмысленный ответ из встроенных знаний без локального `KnowledgeContext` не засчитывается
  как RAG-result;
- серию связанных вопросов с зависимостью от предыдущих реплик;
- явные просьбы о переводе и согласие/отказ после предложения перевода;
- проверку валидности JSON и корректности `action`;
- среднее и максимальное время до первого пригодного фрагмента;
- скорость генерации и длину ответа;
- время от получения финальной фразы до первого полезного результата и до завершения генерации при фиксированных
  `skill_id`, prompt version, generation profile и output schema;
- сравнение минимум двух prompt-профилей (если они рассматриваются) с сохранением их полных версий и состава входа;
- субъективную естественность русского текста после TTS;
- потребление VRAM при одновременной работе с ASR и TTS;
- корректность отмены генерации при перебивании.
- speculative-запросы по расширяющемуся стабильному префиксу ASR;
- отмену speculative-запроса при исправлении промежуточного текста;
- использование prompt/KV-cache для неизменившегося префикса;
- время от финализации ASR до первого пригодного фрагмента ответа после предварительного анализа;
- отсутствие переноса provisional reasoning в финальный запрос после исправления ASR;
- совместимость inference-адаптера с free-threaded CPython либо изоляцию runtime в отдельном процессе; для C3 принят
  отдельный локальный процесс с HTTP IPC.

Приоритет критериев: корректность действия и безопасность перехода состояния, опора на переданный контекст, естественность русского ответа, задержка, затем общий объём знаний модели.

## Последствия

Положительные:

- стартовый кандидат достаточно мал для целевой видеокарты;
- предусмотрен русскоязычный контрольный вариант;
- модель можно заменить без изменения SIP-адаптера и конечного автомата;
- знания предметной области не требуют переобучения модели.

Отрицательные:

- окончательный выбор нельзя сделать только по карточке модели;
- потребуется отдельный адаптер structured output и тесты на некорректный вывод;
- общий бюджет задержки должен делиться между ASR, retrieval, LLM и TTS;
- квантизация может изменить качество и скорость, поэтому вариант квантизации входит в эксперимент.
