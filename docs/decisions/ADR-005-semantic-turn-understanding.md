# ADR-005: семантический ход между финальным текстом ASR и Dialogue FSM

Статус: `accepted`  
Дата принятия: `2026-09-22`

## Контекст

Текущий runtime передаёт один `FinalUserTurn` одновременно в текстовый контекст и непосредственно в `DialogueFSM`.
Такой контракт предполагает одну коммуникативную функцию на одну ASR-реплику. Реальный звонок показал обратное:
реплика `Нет, не надо. Почему небо днём голубое?` одновременно отклоняет предложенный перевод и задаёт новый вопрос.
FSM пыталась классифицировать весь текст как короткое подтверждение, переводила состояние через
`confirmation_unclear` и теряла содержательную часть.

Это типовой случай multi-intent spoken-language understanding. ISO 24617-2 рассматривает вклад участника как один или
несколько функциональных сегментов/dialogue acts, а не требует соответствия «реплика = одно действие».

## Решение

Между `FinalUserTurn` и потребителями диалога вводится typed semantic boundary:

- `DialogueExpectation` — компактное read-only ожидание текущего состояния FSM, например подтверждение перевода;
- `DialogueAct` — типизированная коммуникативная функция с исходным span и содержательными данными;
- `SemanticTurn` — исходный `FinalUserTurn` и упорядоченный непустой набор acts;
- `SemanticTurnParser` — владелец state-aware интерпретации финального текста.

Для принятого MVP parser использует детерминированный fast path: распознаёт явные подтверждения/отказы, прямую просьбу
о переводе и сохраняет содержательный остаток как отдельный knowledge request. Если управляющий act не распознан
однозначно, parser не исполняет критическое действие и сохраняет реплику как содержательный запрос либо запрашивает
уточнение по явно определённой policy.

`DialogueFSM` остаётся единственным владельцем semantic call state и необратимых действий. Parser не переводит звонок,
не запускает inference и не изменяет FSM. `ConversationPipeline` получает содержательный act по прямому typed
data-plane вызову; Event Bus и Dispatcher не переносят крупный текст.

Один `SemanticTurn` обрабатывается в исходном порядке acts. Отказ от pending transfer сначала возвращает FSM в
`LISTENING`, после чего knowledge request того же хода может запустить обычный RAG/LLM path. Исходный пользовательский
текст сохраняется в `ContextStore` ровно один раз; производный content span не становится дублирующим user turn.

Положительное подтверждение, сопровождаемое содержательным остатком, не запускает перевод немедленно. FSM сохраняет
typed pending transfer intent, обрабатывает knowledge request, озвучивает ответ и после завершения playback повторно
спрашивает подтверждение перевода. Только новое положительное подтверждение без предшествующего необработанного content
запускает transfer. Если content path сам завершился `offer_transfer`, это предложение одновременно является требуемым
повторным вопросом и не дублируется вторым playback. `clarify` не считается ответом, завершающим content path: pending
reconfirmation сохраняется до содержательного ответа, явного отказа, transfer или закрытия звонка.

LLM-парсер неоднозначных формулировок в это решение не входит. Typed contracts должны позволять добавить его позднее
как другую реализацию `SemanticTurnParser`, но compatibility fallback или второй скрытый interpretation path не
создаётся.

## Рассмотренные альтернативы

### Расширить набор строк в `_is_positive`/`_is_negative`

Отклонено как целевая архитектура: исправляет отдельные фразы, но всё равно трактует ход как одно действие и продолжает
терять содержательный остаток.

### Передавать составную реплику напрямую answer LLM

Отклонено: модель не должна непосредственно исполнять SIP/control actions; кроме того, retrieval должен получить
содержательную часть до генерации ответа.

### Всегда вызывать LLM как semantic parser

Отложено как отдельное возможное расширение. Оно добавляет inference latency и новую failure/cancellation boundary даже
для простых `да`/`нет`. Необходимость должна быть доказана corpus evaluation неоднозначных реплик.

### Специализированная обученная intent/slot model

Не выбирается для MVP: потребует размеченного русского корпуса и model lifecycle. Typed boundary не запрещает такую
реализацию в будущем.

## Последствия

Положительные:

- составной ход не теряет ни управляющее, ни содержательное действие;
- положительное подтверждение не обрывает вопрос, добавленный пользователем в той же реплике;
- критичные SIP-действия остаются детерминированными и валидируются FSM;
- RAG получает очищенный content span вместо служебной части подтверждения;
- raw ASR text, semantic acts и фактическое действие можно независимо диагностировать;
- parser можно тестировать без GPU и телефонного стенда.

Отрицательные:

- меняется typed boundary между speech, dialogue и conversation pipeline;
- FSM получает scoped pending-transfer/reconfirmation lifecycle для compound positive turn;
- потребуется расширить отчёт и regression corpus;
- новая точка расширения требует защиты от появления двух расходящихся interpretation paths.
