# SIP-бот: техническое задание MVP

Статус: черновик, уточняется вместе с реализацией.

Документ фиксирует технические решения, которые дополняют [постановку задачи](requirements.md). Он не описывает production-эксплуатацию и не включает реализацию PBX.

## 1. Зафиксированные ограничения

- Основной язык реализации — Python.
- Приоритетная среда выполнения — CPython 3.14.x free-threaded (`3.14t`, сборка Python с отключённым GIL, `--disable-gil`). Первичный baseline — Python 3.14.7 на Ubuntu 24.04 LTS x86_64 в WSL2.
- Python 3.15 не используется как основной runtime до отдельной проверки; после стабилизации MVP допускается экспериментальная compatibility-проверка 3.15t.
- Язык общения — русский.
- Одновременно обслуживается один разговор.
- Система запускается в Linux-среде внутри Hyper-V/WSL.
- Для продолжения работы проекта на Windows и в целевой Linux/WSL-среде должен сохраняться запас свободного места не
  менее 20 ГБ; это operational guard для моделей, кэшей, сборок и evidence, а не пользовательский runtime-контракт.
- Целевой GPU — NVIDIA RTX 5060 Ti, доступный объём видеопамяти — до 16 ГБ.
- SIP-медиакодек MVP — PCMU (G.711 μ-law), 8 kHz, mono.
- ASR, LLM и TTS работают локально.
- База знаний для первых тестов строится на тематическом срезе русскоязычной Википедии по естественным наукам.
- Бот не выполняет запись разговоров в своём runtime. Для live-тестов и rehearsal запись выполняется на стороне локального
  Baresip test peer и сохраняется в evidence/artifacts; это диагностическая функция тестового стенда, а не функция бота.
- Реальные внешние сервисы не подключаются; операторская инфраструктура будет эмулироваться локально на этапе тестирования.
- Для публичного исследовательского демонстратора допускаются компоненты с некоммерческими лицензиями при соблюдении [лицензионной политики](licensing-policy.md).
- Совместимость с free-threaded CPython является обязательным критерием для Python-пакетов, native-модулей и Python-обёрток, непосредственно импортируемых основным процессом.
- Компонент, который автоматически включает GIL обратно, не допускается в основном процессе; при необходимости он выносится в отдельный процесс с явным IPC-контрактом.
- Принятый SIP/media-кандидат PJSUA2/PJMEDIA `2.17` для CPython `3.14t` собирается только с двумя compatibility-патчами
  generated SWIG wrapper, зафиксированными в [плане C1](plans/plan-001-C1-sip-pjsua2-pjmedia.md): declaration `Py_MOD_GIL_NOT_USED`
  и исправление границы Python buffer API. Непатченный wrapper не является допустимым baseline; точное содержимое патчей
  хранится в `artifacts/feasibility/001-C1-sip-pjsua2-pjmedia/patches/` и повторно не переписывается в ТЗ.

## 2. Архитектура MVP

Сквозное разбиение компонентов, границы control plane и data plane, а также жизненный цикл каналов описаны в [архитектурном документе](architecture.md).

На этапе MVP предполагается одно основное Python-приложение с компонентами, работающими в отдельных потоках, задачах `asyncio` или процессах в зависимости от выбранного runtime. Основной процесс запускается на CPython 3.14t; несовместимый native runtime допускается только в отдельном процессе. Конкретный способ исполнения не должен менять контракт центрального Dispatcher и каналов данных.

SIP-адаптер является границей проекта с внешней SIP-инфраструктурой. Внутренняя логика PBX, список операторов и правила маршрутизации PBX не реализуются.

### 2.1. Boundary adapters и преобразование потоков

Граница между компонентами не считается прямым подключением очередей. Если формат, размер фрейма, темп выдачи или
lifecycle producer/consumer различаются, между ними создаётся отдельный boundary adapter с собственным владельцем,
ограниченным хранилищем, политикой переполнения, timer/flush policy, cancellation и evidence.

Для аудио MVP предусматриваются следующие преобразования:

- `PJSUA2/PJMEDIA` для каждого конкретного звонка выдаёт media-кадры по параметрам, извлечённым из согласованного SDP и
  соответствующих словарей/объектов PJMEDIA: как минимум codec, payload type, `ptime`, sample rate, channels и frame size.
  Базовым MVP остаётся PCMU/G.711 μ-law 8 kHz mono, но фактический per-call media profile не зашивается предположением и
  фиксируется в evidence;
- `Media format adapter` преобразует PCMU/RTP-facing данные во внутренние PCM S16LE mono 8 kHz кадры и обратно;
- `PCM fan-out` распределяет bounded поток кадров между VAD и ASR input boundary;
- `ASR input accumulator/chunker` собирает media-кадры в настраиваемые chunks для ASR. Начальный конфигурационный
  кандидат — `asr_chunk_ms = 1000`; chunk выдаётся по заполнению или timer policy, а укороченный остаток принудительно
  flush-ится при hard endpoint, close или cancellation. VAD при этом получает кадры без ожидания заполнения ASR chunk;
- `TTS output buffer/framer/pacer` принимает потоковые PCM chunks произвольного размера, накапливает их, формирует
  media-кадры с согласованным `ptime` и выдаёт их по media clock. Накопитель имеет динамическую текущую длину:
  несколько chunks могут составить один frame, один chunk — несколько frames, а остаток сохраняется между тактами.
  Это bounded storage с явным high-water/backpressure/error поведением, а не фиксированная ёмкость одного chunk и
  не truly unbounded buffer. Хвост flush-ится при завершении генерации, а при barge-in закрывается без доставки
  stale audio. Нормальный PCM не может молча теряться из-за отказа `push()`.

Эти adapters являются отдельными компонентами карты взаимодействий. Обычная очередь может использоваться внутри них
как примитив bounded delivery, но не заменяет накопление, таймер, переформатирование, pacing или правила завершения.

### 2.2. LLM Facade и внешний inference process

Ollama является внешним для основного приложения локальным процессом. В основном процессе работает отдельный `LLM Facade`,
предоставляющий остальным компонентам внутренний typed API. Фасад — единственный владелец HTTP IPC к `127.0.0.1` и
единственное место преобразования внутренних request/command в Ollama JSON/stream и обратно.

Внутренний API фасада должен покрывать как минимум: запрос authoritative inference, поток промежуточных результатов,
финальное structured decision, текст ответа, статус, timeout и cancellation. Для RAG тот же фасад предоставляет отдельную
typed-операцию `EmbeddingRequest`/`EmbeddingResponse`, скрывающую Ollama `/api/embed`. Dispatcher, TTS, Context/KB Manager
и другие компоненты не обращаются к Ollama напрямую и не зависят от формата его внешнего протокола.

### 2.3. Skill & Prompt Manager

Между `Dialogue FSM`/контекстом и `LLM Facade` работает отдельный `Skill & Prompt Manager`. Он не является частью
транспортного фасада и не исполняет SIP-команды. Его задача — по финальному пользовательскому ходу, разрешённому FSM
`skill_id` или режиму обработки, snapshot контекста, найденным фрагментам знаний и ограничениям ответа собрать
версионируемый prompt и передать фасаду типизированный `LlmRequest`.

Менеджер владеет registry навыков, шаблонов, output schema и generation profiles. Каждый такой объект имеет стабильный
идентификатор и версию; версия шаблона/profile сохраняется в диагностике и в evidence benchmark. Пользовательский текст
вставляется в prompt как данные с явными границами и не должен молча заменяться, сокращаться или получать новый смысл.
Менеджер может выбирать разные инструкции для ответа, уточнения, предложения перевода и других разрешённых FSM действий,
но не может сам инициировать эти действия или обходить проверку `Dialogue FSM`.

Для MVP исходные шаблоны, skill profiles, output schema и их версии хранятся в виде именованных констант в
`config/constants.py`, вместе с остальной конфигурацией. Формат registry и граница между статическими настройками и
кодом уточняются в child plan; динамическая административная настройка не требуется. Benchmark LLM обязан использовать
тот же prompt/profile и output schema, что и authoritative demo-path, либо явно помечать отличие.

### 2.4. Локальный RAG и база знаний

Работа с локальной базой знаний обязательна для answer path и должна быть отделена от встроенных знаний базовой LLM.
`Context/KB Manager` подготавливает небольшой заранее выбранный русскоязычный корпус по естественным наукам, делит
документы на фрагменты, сохраняет метаданные источника и строит локальный индекс. Каждый runtime-hit должен позволять
восстановить исходный документ/фрагмент и его идентификатор.

Первичный кандидат semantic retrieval — embedding-модель, доступная через локальный Ollama `POST /api/embed`. Вызовы
для построения индекса выполняются заранее; во время звонка embedding строится только для запроса, после чего приложение
само выполняет similarity search и выбирает ограниченное число `top-k` фрагментов. Ollama не владеет документами,
индексом, поиском или решением о достаточности контекста. Конкретная embedding-модель и формат локального индекса
проверяются отдельным execution-slice `002-F` и не считаются принятыми только по наличию endpoint.

Для минимального MVP допускается компактный локальный индекс без Chroma/Qdrant/FAISS, если он обеспечивает воспроизводимый
поиск, сохранение метаданных и проверяемую similarity-оценку. Добавление отдельной vector database не является целью
само по себе. Lexical retrieval может быть только явно согласованным резервным вариантом после провала embedding-кандидата;
автоматическая подмена без owner decision запрещена.

`KnowledgeContext` содержит найденные фрагменты, источники, оценки релевантности и признак достаточности. При отсутствии
достаточно релевантных фрагментов prompt должен приводить к `offer_transfer`/unknown-answer, а не выдавать ответ модели
как будто он подтверждён базой знаний. В evidence отдельно фиксируются: версия корпуса, версия embedding-модели,
параметры chunking/index, query, top-k, scores, использованные источники и признаки того, что ответ действительно
строился на переданном контексте.

## 3. Конфигурация

Вся конфигурация MVP хранится в отдельном файле с набором констант:

```text
config/constants.py
```

Динамическая загрузка конфигурации, административная панель и база настроек в MVP не требуются. Изменение констант вступает в силу после перезапуска приложения.

В файл конфигурации входят как минимум:

- параметры SIP-адаптера и локального RTP;
- принудительный выбор PCMU и частоты 8 kHz;
- адрес/номер оператора для перевода;
- пути к моделям ASR, LLM и TTS;
- параметры inference runtime и выбор GPU/CPU;
- версия Python и режим free-threaded/GIL-enabled для основного процесса и изолированных runtime;
- пути к базе знаний и индексу retrieval;
- каталог файлов текущих разговоров;
- пороги VAD и параметры определения конца реплики;
- media `ptime`, внутренний PCM frame size, `asr_chunk_ms`, chunk timer/flush и ёмкости bounded audio buffers;
- параметры TTS output buffering/re-framing/pacing и допустимый хвост при завершении генерации; per-call media profile
  (`ptime`, payload type, sample rate, channels) при этом извлекается из SDP/PJMEDIA, а не задаётся константой;
- параметры внутреннего `LLM Facade`: HTTP endpoint, stream/read timeouts, cancellation и лимиты request/response;
- параметры `Skill & Prompt Manager`: набор констант skill/template registry, выбранные версии prompt и output schema,
  generation profile, лимит ответа и правила подстановки пользовательского текста;
- параметры RAG: путь к подготовленному корпусу и индексу, версия embedding-модели, `top_k`, порог релевантности,
  лимит объёма передаваемого контекста и политика unknown-answer;
- параметры `Transcript Assembler`, включая правило стабилизации partial ASR-гипотез: общий префикс соседних revisions не
  фиксируется автоматически, stable prefix принимается только из явного backend-поля;
- порядок pre-call warmup stages и критерий readiness: RAG/embeddings, structured LLM chat, ASR operation и первый TTS
  PCM chunk должны быть успешно выполнены до допуска SIP-вызова;
- soft/hard endpointing и минимальную длительность речи;
- порог и режим использования advisory `completion_hint` от LLM;
- целевые значения задержки и параметры журналирования.

Параметры локальной эмуляции и возможные тестовые учётные данные хранятся в том же файле констант. Подключение к реальным внешним сервисам и проектирование production-хранилища секретов не входят в MVP.

Конкретный выбор LLM пока не считается окончательно утверждённым. Текущий shortlist включает Qwen3.5-9B как основной новый кандидат, Qwen3.5-4B как быстрый baseline, Qwen3-8B как baseline скорости, Vikhr-Llama3.1-8B-Instruct-R как русскоязычный контрольный вариант, а также Qwen3.6-27B/Qwen3.8-27B как stretch-кандидаты. Обоснование, ограничения VRAM и план проверки приведены в [ADR-002](decisions/ADR-002-llm-model-selection.md).

## 4. Сигнальный интерфейс

Между dialogue manager и SIP-адаптером используется явный интерфейс событий и команд. Управление SIP не передаётся модели в виде свободного текста.

### Протокольная реакция SIP-адаптера

SIP-адаптер обязан самостоятельно и с ограниченным временем ожидания обрабатывать протокольные транзакции и
обязательные ответы. Он не должен ждать Dispatcher, ASR, LLM, TTS или отчёт. В эту категорию входят `BYE`, `CANCEL`,
`OPTIONS`, `re-INVITE`/`UPDATE`, изменения media-направления при hold/resume, RTP timeout и транспортные ошибки.
`BYE` остаётся обязательным тестовым примером, но не исчерпывает контракт.

После протокольной реакции адаптер публикует нормализованное прикладное событие, если оно влияет на FSM или жизненный
цикл каналов. Dispatcher владеет смысловым решением, но не является обязательным звеном для ответа на SIP-транзакцию.

### События от SIP-адаптера

- `call_started`;
- `call_answered`;
- `remote_hangup` / `remote_cancel`;
- `remote_hold_started` / `remote_resumed`;
- `media_reconfigured`;
- `rtp_timeout` / `media_failed`;
- `sip_transaction_error`;
- `transfer_completed`;
- `transfer_failed`;
- `media_started` / `media_stopped`.

### События от audio pipeline

- `speech_started`;
- `pause_candidate`;
- `soft_endpoint`;
- `speech_resumed`;
- `hard_endpoint`;
- `utterance_final`;
- `barge_in`;
- `audio_overrun` / `audio_underrun`.

### Команды dialogue manager к SIP-адаптеру

- `answer()`;
- `hangup()`;
- `transfer(target)`;
- открыть/закрыть входящий и исходящий media-каналы;
- отменить текущий playback/TTS-поток.

Фактический механизм перевода, например SIP REFER или функция конкретной PBX, инкапсулируется SIP-адаптером. Для dialogue manager результатом является успешное или неуспешное выполнение команды `transfer(target)`. Аудиофреймы TTS не проходят через dialogue manager и передаются напрямую в playback-канал.

### Тактовая выдача media и намеренная тишина

PJMEDIA запрашивает исходящие кадры по согласованному media clock и `ptime`, тогда как потоковый TTS выдаёт PCM
порциями произвольного размера и с недетерминированными интервалами. Поэтому выход playback должен иметь логический
выбор источника непосредственно перед media buffer/adapter boundary:

- в состоянии `IDLE`, `CANCELLED` или `CLOSED` выдаётся заранее подготовленный кадр тишины;
- в состоянии `PREROLL` ожидание первого PCM измеряется отдельно как `tts_startup_wait`;
- в состоянии `PLAYING` кадры берутся только из TTS-буфера;
- пустой TTS-буфер в состоянии `PLAYING` увеличивает `egress_underruns` и временно заполняется тишиной как аварийным
  fallback, не скрывая событие.

Тишина не помещается бесконечным потоком в тот же bounded TTS-буфер: это могло бы вытеснить или задержать полезные
кадры. Выбор источника является частью существующего playback/media owner и не требует нового control-plane маршрута
для PCM. Переходы между режимами выполняются по существующему lifecycle playback; сам callback выдачи остаётся
коротким и неблокирующим. Исправление целостности накопления и проверка полного audible output выполняются в
`005-E`; оно не добавляет межкомпонентный сигнал или новый delivery owner.

## 5. Состояние и контекст разговора

Контекст не должен бесконечно накапливаться только в prompt LLM. Для каждого звонка создаётся отдельный каталог:

```text
data/dialogues/<call_id>/
```

Обязательный артефакт результата звонка — только:

- `report.md` — итоговый документ, создаваемый после завершения звонка.

Для внутренней работы приложение может дополнительно вести:

- `conversation.jsonl` — дописываемый журнал текстовых событий разговора.

Этот журнал и любые компактные in-memory snapshots являются implementation
details. Они не являются обязательными внешними артефактами и не должны
появляться в acceptance только потому, что удобны для реализации.

В `conversation.jsonl` сохраняются финальные реплики пользователя и бота, существенные результаты retrieval, решения dialogue manager, команды перевода и события завершения звонка. Промежуточные ASR-гипотезы не обязательны для сохранения.

При формировании следующего запроса к LLM используются:

- ограниченный текущий snapshot контекста, сформированный владельцем контекста
  в памяти; при наличии — данные внутреннего `conversation.jsonl`;
- последние релевантные реплики;
- найденные фрагменты локальной базы знаний;
- текущий вопрос и состояние диалога.

После завершения звонка пост-обработка создаёт `report.md`. Отчёт может содержать:

- идентификатор и временные границы разговора;
- текстовую последовательность основных реплик;
- краткое резюме цели пользователя и результата;
- вопросы, на которые бот ответил или не ответил;
- использованные источники знаний;
- факт и результат перевода на оператора;
- причину завершения разговора.

Аудиофайлы в каталог диалога ботом не записываются. Файлы записи тестового стенда хранятся отдельно в
`artifacts/implementation/<map>/<run>/recordings/` и не являются частью runtime-состояния диалога.
Для Baresip `sndfile` test-peer recording исходные `enc` и `dec` сохраняются как primary evidence. Если их длины
различаются из-за разного момента закрытия media-пайплайнов, stereo derivative выравнивает только хвост более короткой
дорожки явными нулевыми PCM-кадрами; mapping, policy и число добавленных кадров обязательно записываются в manifest.

## 6. Правила диалога и эскалации

LLM должна возвращать не только текст, но и структурированный результат принятия решения. Минимально необходимы следующие типы результата:

- `answer` — подготовить текстовый ответ;
- `clarify` — задать уточняющий вопрос;
- `offer_transfer` — сообщить, что бот не может надёжно ответить, и спросить о подключении оператора;
- `transfer` — немедленно перевести звонок;
- `hangup` — завершить разговор.

Минимальный формат результата LLM:

```json
{
  "action": "answer",
  "text": "Краткий ответ пользователю"
}
```

Поле `text` обязательно для `answer`, `clarify` и `offer_transfer`; для `transfer` и `hangup` оно может отсутствовать. Цель перевода не передаётся моделью: адрес или номер оператора берётся менеджером диалога из конфигурации. Менеджер валидирует JSON и допустимость действия в текущем состоянии, поэтому некорректный или недопустимый результат LLM не исполняется напрямую.

Ответ для телефонного канала должен быть на русском языке, коротким, пригодным для TTS и без Markdown, служебных рассуждений и комментариев о внутреннем prompt. История LLM должна содержать только финальные ответы, а не скрытое содержимое режима рассуждений.

Правила эскалации:

1. Если в базе знаний нет достаточной опоры для ответа или модель не может надёжно сформировать ответ, бот сообщает об ограничении и предлагает подключить оператора.
2. Положительное подтверждение пользователя приводит к `transfer(configured_operator_target)`.
3. Явная просьба пользователя о переводе приводит к `transfer(configured_operator_target)` без дополнительного подтверждения.
4. Отрицательный ответ на предложение перевода возвращает разговор в обычный режим; бот может попросить уточнить вопрос или завершить разговор по правилам диалога.
5. После отправки команды перевода бот прекращает генерацию и озвучивание, освобождает ресурсы разговора и ждёт результата SIP-адаптера.

## 7. Потоковая обработка и перебивание

- RTP-аудио принимается непрерывно, в том числе во время речи бота.
- ASR должен поддерживать промежуточные результаты.
- `Transcript Assembler` заменяет промежуточные ASR-гипотезы целиком, отделяет явно подтверждённый backend-полем стабильный
  префикс от изменяемого хвоста и выдаёт финальный текст по сигналу endpointing. Совпадение префиксов соседних гипотез не
  считается достаточным доказательством стабильности, поскольку ранняя ошибка распознавания может повторяться.
- Стабильный промежуточный текст может передаваться в speculative LLM/retrieval pipeline до завершения пользовательского хода.
- Только финальный текст ASR является основанием для окончательного решения LLM, изменения состояния FSM и разрешения озвучивания.
- LLM должна по возможности выдавать результат частями.
- TTS начинает работу после получения первой пригодной для произнесения фразы.
- При обнаружении речи пользователя во время TTS воспроизведение прекращается.
- Незавершённая генерация LLM и TTS отменяется, если это поддерживает выбранный runtime.
- Новая пользовательская реплика получает приоритет и записывается в состояние разговора.

Начальная эвристика endpointing: soft endpoint ориентировочно 250–300 ms тишины используется для упреждающей обработки, hard endpoint ориентировочно 500 ms непрерывной тишины — для финализации хода. Оба значения являются конфигурационными и должны проверяться на тестовых разговорах.

## 8. Бюджет задержки

Основная пользовательская метрика — время от окончания речи пользователя до первого полезного звука ответа.

```text
T_total = T_RTP + T_AI
T_AI = T_endpointing + T_ASR + T_retrieval + T_LLM + T_TTS
```

Для расчёта фиксированно резервируется 30 ms на RTP/media-транспорт; отдельное измерение сетевой задержки в MVP не выполняется. Рабочий целевой диапазон суммарной задержки — 200–500 ms, то есть ориентировочный бюджет AI-конвейера составляет 170–470 ms. Эти значения являются инженерной целью, основанной на ориентирах пользовательского комфорта из ITU-T, а не нормативным требованием к отдельной модели.

Порог hard endpoint входит в `T_endpointing`. Speculative ASR/LLM/retrieval может выполняться до финализации и уменьшать остаточную задержку после окончания речи, но не отменяет необходимость подтвердить окончательный текст.

Измерения должны сохранять временные отметки минимум для:

- окончания пользовательской реплики;
- решения endpointing;
- финального ASR;
- первого результата retrieval;
- первого пригодного фрагмента LLM;
- первого аудиофрагмента TTS;
- отправки первого RTP-фрейма.

## 9. Критерии технической готовности

- Конфигурация меняется через отдельный файл констант.
- Приложение запускается на CPython 3.14.7 free-threaded (`3.14t`) в Ubuntu 24.04 LTS x86_64.
- Импорт критичных зависимостей не включает GIL обратно; это проверяется в чистом процессе и после выполнения сценариев с ленивыми импортами.
- Для каждой зависимости с C/C++-расширением зафиксированы версия, wheel/source build, результат проверки `sys._is_gil_enabled()` и решение об основном процессе либо process isolation.
- Для PJSUA2/PJMEDIA build provenance включает применение обоих C1 compatibility-патчей и hash итогового native extension;
  сборка без них считается неподдерживаемой конфигурацией для этого MVP baseline.
- Один звонок проходит полный цикл от SIP-сигнализации до завершения.
- PCMU-аудио корректно принимается, преобразуется для моделей и возвращается в SIP.
- Промежуточные ASR-гипотезы собираются без накопления исправленных фрагментов.
- Возобновление речи до hard endpoint отменяет speculative-обработку и продолжает текущий пользовательский ход.
- После hard endpoint создаётся один финальный текст пользовательского хода.
- Контекст разговора дописывается в файл без записи аудио со стороны бота; запись test peer относится к evidence стенда.
- После завершения звонка создаётся итоговый `report.md`.
- Бот умеет ответить, уточнить вопрос, предложить перевод и выполнить перевод.
- Явная просьба о переводе обрабатывается без дополнительного подтверждения.
- Перебивание прекращает текущую речь бота и не ломает состояние диалога.
- `Skill & Prompt Manager` формирует `LlmRequest` из финального хода, контекста, знаний и разрешённого FSM-профиля;
  в evidence видны идентификаторы/версии шаблона и generation profile.
- RAG-контур возвращает source-aware `KnowledgeContext`; ответ по встроенным знаниям модели без локального hit не
  считается выполнением требования работы с базой знаний.
- До допуска вызова application runtime успешно выполняет pre-call warmup для RAG/embeddings, LLM chat, ASR и TTS; при
  ошибке или неполном результате этапа вызов не принимается, а время и результат каждого этапа сохраняются в evidence.
- Временные отметки позволяют вычислить суммарную задержку и её составляющие.

## 10. Решения, которые предстоит уточнить при реализации

- способ сборки/поставки CPython 3.14.7t для WSL и воспроизводимость этого runtime;
- production implementation details поверх принятого PJSUA2/PJMEDIA baseline и способ взаимодействия с внешним SIP-участником;
- конкретные локальные модели и inference runtime для русского языка; кандидаты и порядок проверки описаны в [ADR-002](decisions/ADR-002-llm-model-selection.md);
- набор навыков, шаблонов, generation profiles и окончательная схема `LlmRequest`;
- embedding-модель и формат индекса RAG, а также окончательные `top_k`/relevance threshold;
- окончательная схема структурированных ответов LLM и способ её потокового разбора на этапе реализации.

Проверка Python runtime и critical native dependencies выполняется первым feasibility-срезом до реализации основной логики. Детальные правила gate приведены в [ADR-003](decisions/ADR-003-free-threaded-python.md).
