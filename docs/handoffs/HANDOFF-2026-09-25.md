## Опорная схема размещения для развёртывания

Схема из handoff 24.09 сохранена без замены адресов наблюдениями текущего теста. В таблице перечислены роли узлов и проверенные тогда маршруты; это **не** утверждение, что все процессы запущены сейчас.

| Узел | Назначение | Адрес/маршрут из handoff 24.09 |
|---|---|---|
| WSL `Ubuntu-24.04` | SIP-бот, web backend, WSS-forwarder, локальная Ollama | web `:8080`/HTTPS `:8443`; Ollama `127.0.0.1:11434`; bot SIP `172.16.15.72:15062` |
| WSL `Debian-Bookworm-FS` | FreeSWITCH и `mod_callcenter` | browser WSS `192.168.1.74:7443`; профиль `bot-vpn` SIP/RTP `172.16.15.72:15062`; общая очередь `7100` |
| Windows-хост | разработка и браузер | `https://172.16.15.72:8443/` |
| Телефон в LAN | браузер и QR | `https://192.168.1.74:8443/`, с принятием временного сертификата |

Два IP web-страницы относятся к **одному** backend в Ubuntu. В исходной репетиции Windows не открывал собственный LAN-IP `192.168.1.74:8443` в WSL mirrored режиме, поэтому использовался `172.16.15.72`. Для браузерного микрофона нужен HTTPS. Маршрут WSS для Windows в репетиции: Ubuntu `:17445` → Debian `:17443` → FreeSWITCH `:7443`; телефон в LAN шёл непосредственно на `:7443`. SIP From user передаётся в caller ID через сохранённый dialplan `config/workshops/20_workshop_callcenter.xml`, иначе бот не найдёт корпус по caller ID. Конфигурация FreeSWITCH и сетевые оговорки — в `config/workshops/` и `demo-web/README.md`.
