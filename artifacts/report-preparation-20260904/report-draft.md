# SIP-бот с локальными ASR, RAG/LLM и TTS: черновик доклада

Статус: технически подтверждённый рабочий черновик; Map-006 corrective target r6 принят, downstream claims требуют редакционного refresh  
Дата: `2026-09-04`

## Аннотация

Демонстратор показывает полный локальный голосовой контур: SIP/RTP-вызов с PCMU, потоковое распознавание русской
речи, поиск по локальной базе знаний, генерация ответа локальной LLM, потоковый синтез речи и возврат ответа в
звонок. Архитектура рассчитана на один параллельный разговор и специально отделяет протокол/состояние звонка от
тяжёлых AI-контуров. Проект является MVP и исследовательским демонстратором, а не production-системой.

Источники и точные результаты собраны в [`source-index.md`](source-index.md), воспроизводимый запуск — в
[`demo-runbook.md`](demo-runbook.md).

Редакционное ограничение: r7 подтверждает сценарий, RAG, SIP и recording baseline, но пользовательское прослушивание
выявило потерю части TTS output. `005-E` исправил дефект, а r10 подтвердил полный слышимый output; текущие claim и
связанные counters уже обновлены по r10. Документ остаётся черновиком для содержательной редакции владельцем.

## 1. Задача и границы

Нужно было проверить, можно ли собрать локального голосового SIP-бота на машине с RTX 5060 Ti/16 ГБ VRAM,
сохранив естественный диалог, контекст, перебивание и перевод на оператора. Пользовательский вопрос не должен
уходить во внешние AI API. База знаний загружается заранее; если в ней нет подтверждения ответа, бот предлагает
оператора.

В MVP входят один русский SIP-разговор, PCMU, локальные ASR/LLM/TTS, обязательный RAG, multi-turn context, barge-in,
перевод на локально эмулируемого оператора и итоговый текстовый отчёт. Не входят PBX, многосессионная нагрузка,
production HA/SLO/security, MOS/load campaign и production retention аудио.

## 2. Архитектурная идея

Сигнальный и голосовой контуры разделены.

```text
SIP/PJMEDIA
   ├─ control plane → Dispatcher → DialogueFSM/CallSession
   └─ data plane → PCM fan-out → VAD/endpointing/ASR
                              → FinalUserTurn → RAG/Prompt → LLM Facade/Ollama
                              → TTS chunks → buffer/pacer/playback → PJMEDIA/RTP
```

Dispatcher принимает только компактные управляющие события и решения. Audio и крупные текстовые payloads идут по
прямым typed boundaries или bounded thread-safe queues. Поэтому обязательный SIP-ответ не ждёт LLM: длительный ASR,
LLM или TTS не должен мешать обработке BYE, CANCEL, OPTIONS, re-INVITE/UPDATE и media failures.

LLM не имеет произвольного SIP-доступа. Она возвращает ограниченное structured decision, а FSM валидирует и исполняет
разрешённую команду. Закрытие канала изолирует старое поколение ответа; перебивание оставляет входящий audio path
активным.

## 3. Компоненты и технологии

- SIP/media: PJSUA2/PJMEDIA с negotiated per-call media profile; baseline — PCMU, 8000 Hz, mono, ptime 20 ms.
- ASR: faster-whisper с multilingual Whisper large-v3 и узким patch для free-threaded CTranslate2 binding.
- RAG: локальный corpus по естественным наукам, embeddings через `embeddinggemma`, локальный vector index и source IDs.
- LLM: Qwen3.5-9B Q4_K_M через локальный Ollama HTTP process. Это изолированный native inference boundary; Python
  controller остаётся no-GIL.
- TTS: XTTS-v2, потоковая выдача PCM; output агрегируется и перевыравнивается к negotiated media ptime.
- Runtime: Ubuntu 24.04/WSL2 и CPython 3.14.7t с `gil_enabled=false`.

Для ускорения ответа есть отдельный Skill & Prompt Manager: он формирует запрос из final user turn, истории и
релевантного RAG-контекста, а также задаёт профиль ответа. При этом обязательность RAG не заменяется модельным
ответом без источников.

## 4. Что показал финальный прогон

Исторический clean-start rehearsal `r7` выполнил J4 с результатом `pass` и 6/6 сценарными проверками; upstream
corrective clean-start `r10` подтвердил TTS integrity. Текущий corrective target Map-006 `r6` подтвердил полный
демонстрационный сценарий:

- follow-up использовал контекст предыдущего вопроса;
- barge-in завершил старое воспроизведение и позволил обработать новый ход;
- вопрос вне базы знаний вызвал offer transfer;
- ответ пользователя «Да» перевёл вызов на fake operator;
- terminal lifecycle создал `report.md`;
- Baresip test peer сохранил обе стороны разговора.

На target runtime подтверждены `CPython 3.14.7t`, `gil_enabled=false`, PCMU/8000/mono и ptime 20 ms. В r6 пройдены
все 7 обязательных scenario checks; trace содержит 7 пользовательских финализированных ходов, 4 ответа и 6 RAG-
контекстов. В media path: `egress_underruns=0`, callback/dropped errors отсутствуют; intentional silence и startup
wait учитываются раздельно. В TTS output принято `40` chunks, `574298` bytes, `1723` emitted frames и `0` overflow
bytes; остаток старого поколения учтён отдельным счётчиком.

Запись строится на стороне Baresip: raw `enc`/`dec` сохраняются, затем из них формируется stereo WAV с mapping
`left=user_to_bot`, `right=bot_to_user`. Производный файл имеет 2 канала, PCM16, 8000 Hz и длительность `81.48 s`;
выравнивание короткого хвоста (`31040` нулевых кадров) сделано явно и отражено в manifest. Read-only audio audit не
обнаружил прежнего дефекта, при котором после короткого фрагмента TTS остальная часть ответа превращалась в тишину.

## 5. Задержка и прогрев

Пользователь оценивает суммарную паузу, поэтому основная метрика считается от окончания речи пользователя до первого
полезного PCM ответа. В measured AI path:

- first useful LLM output: `488.600 ms`;
- valid structured LLM result: `1518.092 ms`;
- first XTTS PCM: `1785.090 ms` от final phrase.

Таким образом, этот baseline не укладывается в ориентир комфорта `200–500 ms`. Это не скрывается разбиением на
компоненты. Отдельно показывается pre-call warmup `44.49 s`: он выполняет реальные операции RAG/LLM/ASR/TTS до
допуска SIP и не относится к latency уже принятого пользовательского хода.

Главный практический вывод: локальная интеграция и сценарная полнота достигнуты раньше, чем требуемая естественность
задержки. Следующий путь оптимизации — prompt/profile, модельный runtime и совместное планирование AI-ресурсов, а не
маскировка измерения.

## 6. Ограничения и лицензии

Это демонстрационный код для открытого обмена опытом. Исходный код, веса моделей, corpus, голоса и outputs имеют
раздельные условия. Веса не включаются автоматически в репозиторий; перед публикацией нужны `LICENSE`,
`THIRD_PARTY_NOTICES.md`, attribution для corpus/моделей и проверка voice sources. Текущий package фиксирует эти
обязательства, но не объявляет юридическую готовность публичного релиза.

Ограничения MVP: один звонок, WSL2 target, отсутствие production PBX/HA/security/retention, отсутствие полного MOS/load
исследования и отсутствие независимого native cancellation token у XTTS.

## 7. Вывод

Технологический стек уже способен локально провести русский SIP-разговор с RAG, контекстом, перебиванием, эскалацией
и переводом. Архитектурное разделение control/data plane позволяет сохранять протокольную отзывчивость при работе
AI-контуров. Главный незакрытый пользовательский показатель — суммарная задержка ответа; он измерен, воспроизводится
и должен быть показан как ограничение текущего MVP.
