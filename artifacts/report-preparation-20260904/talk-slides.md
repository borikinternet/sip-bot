## Слайд 2. Архитектура: два контура, одна система

**Время:** 3 минуты

**Дата/этап мелкой подписью:** `26–27.08` — baseline SIP/media и окружения; `02–04.09` — typed boundaries и
сквозная интеграция

**Заголовок на слайде:**

> Голос идёт напрямую. Управление — через диспетчер.

**Текст на слайде:**

```text
CONTROL PLANE
SIP signalling ↔ SIP/PJMEDIA adapter ↔ Dispatcher ↔ Dialogue FSM
LLM Facade ───────────── typed decision ───────────────► Dispatcher
                         ▲             │
                         │             │ MediaSessionControl
                   MediaStatus         ▼
MEDIA / DATA PLANE
RTP/PCMU ↔ PJMEDIA → PCM Fan-out → ASR → RAG / Skills → LLM → TTS → PCM buffer → PJMEDIA ↔ RTP/PCMU

MEDIA-CONTROL BOUNDARY
только typed commands/events; raw RTP, PCM и text payload — напрямую
```

Под схемой: `typed boundaries • barge-in • RAG • transfer • media-control boundary`

**Визуальное решение:** горизонтальная двухрядная схема с вертикальной двунаправленной границей между рядами.
Верхний ряд — control plane: SIP signalling, SIP/PJMEDIA adapter, Dispatcher и Dialogue FSM. Нижний ряд — media/data
plane: RTP/PCMU, PJMEDIA, аудио- и текстовый pipeline. Между рядами явно показать две разнонаправленные стрелки:
`MediaSessionControl` вниз и `MediaStatus/MediaEvents` вверх. Рядом с границей разместить подпись `control only`;
не проводить через неё линию PCM/RTP или полный текстовый payload. Отдельная стрелка от `LLM Facade` к `Dispatcher`
показывает, что LLM предлагает typed decision, но не управляет SIP напрямую; сам `LLM Facade` при этом остаётся
границей вызова LLM из data-plane.

**Устный акцент:** SIP signalling находится в control plane, а RTP/PCMU — в media plane. SIP/PJMEDIA adapter является
стыком: он принимает SIP/SDP и управляет медиасессией, но сам аудиопоток идёт в media pipeline. Dispatcher управляет
состояниями, перебиванием, переводом и жизненным циклом звонка через typed commands/events; медиа и крупные данные не
транзитируют через него. В текущем варианте используются PCMU, локальные модели, одна сессия и заранее загруженная
база знаний.

**Заголовок на слайде:**

> AI ускоряет инженерный цикл, но не принимает задачу за специалиста

**Текст на слайде:**

```text
Я                                  AI
требования                         поиск
границы и решения                  код
критерии корректности              тесты
приёмка результата                 evidence и документы

Требование → boundary → тест → запуск → проверка
```

**Визуальное решение:** две колонки с разными цветами и общей нижней стрелкой цикла. Не использовать длинные

**Устный акцент:** специалист выявляет скрытые требования, выбирает компромиссы и оценивает пользовательский
результат. AI берёт на себя большой объём исследовательской, кодовой и документальной работы, но каждая существенная
граница проходит через план, тест и проверку на целевой платформе.

## Слайд 4. Пример: быстрый TTS не означает непрерывный голос

**Время:** 4 минуты

**Дата/этап мелкой подписью:** `04.09` — дефект найден на r7, исправление принято на r10

**Заголовок на слайде:**

> Формально всё работает. Пользователь слышит тишину.

**Текст на слайде:**

```text
TTS генерирует быстрее, чем PJMEDIA читает

Голос → тишина
egress_underruns = 0

Фикс:
dynamic buffer + pacing + generation control
```

Справа или внизу: `7/7 live-сценариев после исправления`

Мелкая подпись под результатом: `r7 — 04.09: потеря TTS output обнаружена • r10 — 04.09: полный output подтверждён`

**Визуальное решение:** две горизонтальные временные шкалы «до» и «после»:

```text
ДО:     ███ голос █ тишина █ тишина █ тишина
ПОСЛЕ:  █████████████ непрерывный голос █████
```

Лучший вариант — дополнить схему фрагментом waveform из стереозаписи или коротко воспроизвести «до/после» во время
доклада. Рядом показать маленькую выноску: `underruns: 0`.

**Устный акцент:** PJMEDIA запрашивает звук тактово, а TTS выдаёт его готовыми чанками. Нужны динамический буфер,
регулярная выдача кадров и корректное отбрасывание устаревших поколений. Это пример того, почему автоматический
тест и счётчик ошибок не заменяют прослушивание пользовательского результата.

## Слайд 5. Техническая точка расширения: заменить RAG

**Время:** 2 минуты

**Дата/этап мелкой подписью:** `03.09` — RAG/index/query evidence; `04.09` — source-aware RAG в полном live-прогоне

**Заголовок на слайде:**

> Стабильный runtime, сменный контур знаний

**Текст на слайде:**

```text
НЕ МЕНЯЕМ                         МЕНЯЕМ
SIP / ASR / TTS / FSM             corpus / embeddings / prompt

Ollama embed • vector store • skills
```

**Визуальное решение:** слева показать неизменяемое ядро `SIP / ASR / TTS / FSM`, справа — сменный пакет
`documents → chunks → embeddings → retrieval → prompt`. Внизу маленькими подписями указать технические точки:
`Ollama /api/embed`, `vector store`, `metadata filter`.

**Устный акцент:** это самый доступный уровень самостоятельной адаптации: меняются знания и правила поведения, но не
медиа-контур и не жизненный цикл звонка. Важно подчеркнуть, что RAG — это не магия Ollama: приложение само отвечает
за разбиение документов, хранение векторов, поиск и сборку prompt.

## Слайд 6. Техническая точка расширения: typed boundaries

**Время:** 2,5 минуты

**Дата/этап мелкой подписью:** `02–03.09` — Map-I и propagation контрактов; `04.09` — end-to-end gate

**Заголовок на слайде:**

> Новая функция начинается с контракта на границе

**Текст на слайде:**

```text
PCM frame 20 ms  →  stream buffer 1 s  →  ASR
TTS chunks       →  dynamic PCM buffer →  PJMEDIA clock
LLM              ↔  HTTP Facade         →  typed decision → FSM

контракт • преобразование • тест границы
```

Внизу: `media plane отдельно • control plane через Dispatcher`

**Визуальное решение:** три горизонтальные мини-схемы преобразования на границах. Над каждой указать разные единицы
и ритм данных: `20 ms`, `1 s`, `chunk`, `decision`. Это должно визуально показать, что компоненты нельзя просто
соединить обычной очередью без согласования формата, времени жизни и владельца буфера.

**Устный акцент:** здесь появляются реальные инженерные доработки: преобразование размеров и темпа данных, отмена
устаревших поколений, изоляция внешнего LLM через HTTP-фасад и передача управляющего решения в FSM. Новая функция
должна начинаться с typed contract и заканчиваться тестом именно на границе.

**Заголовок на слайде:**

**Текст на слайде:**

```text
SIP:       2 call legs • conference • attended transfer • whisper
AI:        emotion • speaker verification • toxicity • history
Business:  CRM • ERP • calendar • tickets • notifications

boundary → contract → test → live gate
```

**Визуальное решение:** веер из трёх технических направлений вокруг ядра `SIP-assistant`:

1. `SIP`: две call leg, конференция, attended transfer, whisper;
2. `AI`: GigaAM-Emo или emotion2vec+, русская классификация текста, toxicity, embeddings;
3. `Business`: CRM/ERP/calendar adapters, ticketing и notification gateway.

Внизу — крупная финальная фраза: `AI ускоряет реализацию; boundary и проверка определяют результат`.

В самом низу отдельная тонкая строка:

```text
← ранее: FreeSWITCH как локальный call-центр
→ далее: настройка SIP-ассистента и загрузка базы знаний в RAG
```

**Устный акцент:** последний слайд показывает не каталог продукта, а карту инженерных точек роста. Для каждой новой
возможности нужно определить источник данных, владельца состояния, typed boundary, реализацию и способ проверки.
Отдельно связать доклад с программой конференции: ранее был показан мастер-класс по настройке FreeSWITCH под нужды
небольшого call-центра, а позже состоится практический мастер-класс по настройке SIP-ассистента под нужды абстрактной
небольшой компании, систематизации её документов и загрузке массива знаний в RAG. Продуктовые сценарии не разворачивать
здесь подробно.
